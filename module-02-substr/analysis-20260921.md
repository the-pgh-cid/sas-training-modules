## The Indexing Trap

### What SAS Does
```sas
first_three = substr(text, 1, 3);   /* Positions 1-3 (1-based) */
middle = substr(text, 5, 4);        /* Positions 5-8 (1-based) */
from_seventh = substr(text, 7);     /* Position 7 to end */
```

SAS uses **1-based indexing**: the first character is at position 1.

### What Python Requires
```python
df['first_three'] = df['text'].str[0:3]    # Indices 0-2 (0-based)
df['middle'] = df['text'].str[4:8]          # Indices 4-7 (0-based)
df['from_seventh'] = df['text'].str[6:]     # Index 6 to end
```

Python uses **0-based indexing**: the first character is at index 0.

### The Hidden Complexity

This isn't just "subtract 1 from the start position." SAS also specifies:
- Fixed column widths: `$20`, `$3`, `$4`, `$14`
- Right-padding with spaces before slicing
- Trailing space preservation in storage

Without these details, the conversion **looks simpler than it is**.

## Variance Analysis

### Prompt A: High Degrees of Freedom

**Prompt text**: "Convert this SAS code to Python."

**Results**:
- **0/3 runs correct** (0% success rate)
- All three used pandas (100% consistency)
- All three used bracket notation `.str[0:3]` (100% consistency)
- **All three made indexing errors** (100% error rate)
- **Different errors across runs** (non-deterministic)

#### Error Breakdown by Run

**A1 Errors**:
- Row 2, `from_seventh`: "oWorld" vs expected "orld"

**A2 Errors**:
- Row 2, `from_seventh`: "World" vs expected "orld"
- Row 3, `middle`: "-to-" vs expected "to-P"

**A3 Errors**:
- Row 2, `from_seventh`: "oWorld" vs expected "orld"
- Row 3, `middle`: "o-Py" vs expected "to-P"
- Row 3, `from_seventh`: "o-Python" vs expected "-Python"

#### Critical Observation

**A2 and A3 made different errors on Row 3, same column (`middle`).**

This is not about "being more careful" or "trying harder." The model is making different decisions about how to handle the indexing conversion when given no explicit rules.

## Why Constraints Matter

### What Prompt A Left Unspecified

1. **Position adjustment formula**: "SAS uses 1-based, Python uses 0-based" is IMPLIED but not STATED
2. **Padding requirements**: SAS `$20` length declaration is in the code, but its semantic meaning (right-pad before slicing) is not obvious
3. **Stop position calculation**: For `substr(text, 5, 4)`, what is the Python stop index? Is it 8 or 9?
4. **Open-ended slices**: Does `substr(text, 7)` become `[6:]` or `[7:]`?
5. **Width preservation**: Should extracted columns preserve their `$3`, `$4`, `$14` widths?
6. **Validation**: How do we know the output is correct?

### What Prompt B Specified

1. **Position adjustment formula**: "Subtract 1 from SAS start position. Python stop = adjusted start + requested length."
2. **Padding requirements**: "Right-pad text with spaces to width 20 before slicing."
3. **Exact slice calls**: `slice(0, 3)`, `slice(4, 8)`, `slice(6, None)`
4. **Width preservation**: "Preserve result widths 3, 4, 14"
5. **Validation**: "Include assertions for widths and these visible triples: [specific values]"
6. **Method constraint**: "Use .str.slice()"

**Result**: Every ambiguity removed, every edge case specified, every validation rule explicit.

## Teaching Strategy

### 1. Lead with Failure

Show Prompt A results first:
- "Here are three independent runs of the same prompt."
- "Notice: all three got it wrong."
- "But they got it wrong in different ways."

This establishes the problem viscerally. Students see that variance is real and uncontrolled.

### 2. Contrast with Module 1

Remind students that Module 1 (MEAN) had zero variance in Prompt A:
- "Why did MEAN work but SUBSTR fail?"
- "Answer: Strong model priors for common operations mask the variance."

This prevents the wrong lesson: "Just pick common operations." The real lesson: "Priors are task-dependent and unreliable."

### 3. Show Non-Determinism

Compare A2 vs A3 on Row 3, middle column:
- A2 produced: "-to-"
- A3 produced: "o-Py"
- Both wrong, both different

This proves variance isn't about the model "getting confused" - it's about **stochastic sampling from an underspecified distribution**.

### 4. Introduce Constraints as Solution

Show Prompt B:
- "Here's the same task with constraints."
- "3/3 runs correct, 0 variance."
- "Constraints don't slow you down - they eliminate rework."

### 5. Generalize the Pattern

"When does Prompt A work?"
- Common operations with strong priors (MEAN, SUM, basic arithmetic)
- But: even then, you're gambling, not engineering

"When should you use Prompt B?"
- Domain-specific operations (SAS functions)
- Edge-case handling (indexing, missing values, formats)
- Production workflows (where rework is expensive)

## Contrast with Module 1 (MEAN)

| Dimension | Module 1 (MEAN) | Module 2 (SUBSTR) |
|-----------|-----------------|-------------------|
| **Prompt A correctness** | 3/3 (100%) | 0/3 (0%) |
| **Prompt A variance** | Zero | High |
| **Model priors** | Strong (pandas.mean is ubiquitous) | Weak (SAS substr semantics are niche) |
| **Edge cases** | None (mean is mean) | Many (padding, indexing, widths) |
| **Lucky consistency** | Yes | No |
| **Lesson** | Constraints redundant here | Constraints essential here |

**Critical insight**: Module 1's zero variance was **not** evidence that Prompt A is reliable. It was evidence that **MEAN** has strong priors. Module 2 reveals what happens when priors are weak.

## Statistical Notes

### Sample Size

**Current**: n=3 per prompt (6 total)

**Sufficient for**: Demonstration of variance existence and direction

**Insufficient for**: Quantitative variance estimation, confidence intervals, effect size calculation

**Recommendation**: Follow-up testing with n=20-30 per prompt for:
- Variance distribution characterization
- Error frequency by category
- Method choice distribution in Prompt A
- Statistical significance testing

### Non-Determinism

The fact that A2 ≠ A3 on the same input proves that variance is **stochastic**, not **systematic**.

**Implication**: Even if we increased model temperature to 0, we'd still see variance from:
- Top-k/top-p sampling
- Beam search randomness
- Prompt interpretation ambiguity

Constraints collapse this distribution to a point.

## Recommendations for Training Materials

### For Instructors

1. **Run Module 1 and Module 2 in sequence**: The contrast teaches the core lesson
2. **Show raw outputs**: Let students see the actual errors, not summaries
3. **Emphasize non-determinism**: A2 ≠ A3 is the proof that this isn't user error
4. **Don't oversell Prompt B**: It's not "better at prompting," it's "removing degrees of freedom"

### For Learners

1. **Calibrate your intuition**: MEAN worked without constraints, SUBSTR didn't - priors matter
2. **Trust constraints, not priors**: Even strong priors can fail on edge cases
3. **Constraints are documentation**: Prompt B reads like a spec - that's the point
4. **Validation is non-negotiable**: Assertions catch errors before they propagate

### For Materials

1. **Add Module 3-10**: Cover the variance spectrum (calibration → maximum variance)
2. **Landmine examples**: Rounding half-away, missing value sorts, PROC FREQ denominators
3. **Multi-step workflows**: Show how variance compounds across dependencies
4. **Cross-model testing**: Do these patterns hold for GPT-4, Gemini, etc?

## Conclusion

Module 2 (SUBSTR) demonstrates that **lucky consistency from Module 1 (MEAN) does not generalize**. When model priors are weak or edge cases are present, Prompt A produces:
- 100% error rate
- Non-deterministic variance
- Different errors on identical inputs

Prompt B achieves:
- 100% correctness
- Zero variance
- Reproducible, validated output

**The lesson**: Constraints don't make the model "smarter" - they make the task **deterministic**. In production workflows, determinism is the difference between engineering and gambling.

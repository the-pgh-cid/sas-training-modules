Keep the implementation and the evidence separate

We are reducing unnecessary choices and building reproducible checks. We are not promising identical model responses.

The candidate function receives input columns only. Expected values are held separately, copied from the existing module 01 fixture snapshot. The notebook is self-contained, so its teaching demonstration does not depend on the companion folder or a model API connection. Review every code cell before executing it in an approved environment.

A controlled A/B exercise should capture first responses before showing the reference solution. A correct A response is a valid result. Do not reinterpret local reference outputs as live-model trials, and do not edit expected values merely to obtain a passing result.

Presenter notes

These notes are also embedded in the PowerPoint. Expand a slide for facilitation guidance and source references.

Slide 01: presenter notes

Purpose: introduce the proposed pilot, not a finished course or approved operating procedure. The audience already knows the analysis. The training makes that knowledge explicit and gives analysts observable evidence for bounded acceptance. Four sessions are proposed at approximately 25 minutes each. Environment access and basic code-running prerequisites need separate preparation. Ask reviewers to assess fit and scope rather than evaluate model brands.

Suggested opening: You already know what the analysis needs to do. This pilot teaches a workflow for directing a candidate translation and checking what it actually did.

The core curriculum, field guide, desk reference and one working MEAN prototype are supplied in this package. Full learner decks for all four sessions are a later production step.

Slide 02: presenter notes

Teach this as a sequence of review gates, not an acronym to memorize. Understand: analyst checks the explanation. Specify: analyst decides consequential requirements. Translate: model proposes one implementation. Check: reviewed code is executed and compared with expectations established separately from the implementation. Improve: optimization or redesign is requested as a distinct step.

Do not promise identical text, output convergence, or guaranteed correctness. The pedagogical focus is on explicit choices and reproducible checks. Behavioral equivalence and identical source text are different ideas. Three passing tests establish bounded evidence, not proof for every input.

Facilitator question: What must remain true before we accept this translation? Follow-up during discussion: What does the current evidence not establish?

Slide 03: presenter notes

Proposed recurring cadence: 5 minutes explanation, 8 demonstration, 8 practice, 4 discussion. Sessions may need adjustment after a pilot group.

Session 1: choose a short, familiar SAS program. Ask for explanation without translation. Learners inspect inputs, transformations, outputs and missing dependencies. Exit evidence: a corrected explanation and one explicit unresolved assumption.

Session 2: use MEAN. Show how the practical headings make consequential choices visible. Capture first A/B responses before revealing the reference implementation. Exit evidence: a bounded request with behavior and output requirements. A working A response is a valid result.

Session 3: use SUBSTR or LENGTH from the existing modules. Walk through known answers, discriminating cases and preservation. Exit evidence: expected versus actual, an acceptance decision, and stated limits.

Session 4: use a small, synthetic read/filter/derive/summarize workflow. Chunk at input/output boundaries, carrying dependencies between units. Test the assembled result, not only isolated pieces. Exit evidence: a reviewed map and a bounded integration record.

Pre-class: confirm approved access, synthetic fixtures, package versions and an available execution path. Do not spend the class on SSH, credentials, or installing Jupyter. Provide captured reference examples for demonstrations, clearly labeled as reference material.

Slide 04: presenter notes

MEAN example: SAS averages nonmissing arguments and returns missing when none is observed. The source rows and calculation are retained from module 01. The pilot introduces a callable Python interface and explicit preservation requirements so both prompt variants can use one harness.

The learner-facing lesson is not which model knows MEAN. It is which choices were supplied, which were inferred, and how the result is checked. Avoid staging an inevitable failure for the open prompt. Capture the first response, inspect it, and execute it separately.

For the demonstration, use only synthetic fixtures and approved inputs. Response-only restrictions keep proposal generation distinct from execution; actual application permissions also need to be configured appropriately.

Slide 06: presenter notes

Show the actual files during review. The four-page field guide is the learner-facing core. The desk reference is US Letter, intended for two-sided long-edge printing. The existing module PDFs remain worked examples rather than being copied into a competing curriculum.

The MEAN .ipynb is self-contained: it embeds the exact fixture snapshot, supplied reference, and adapted harness. It needs an approved Python kernel with pandas, but no Bedrock API call. A static HTML export lets non-notebook users review the content and local execution output. It is not executable.

Portal route: obtain a response through the approved interface, retain it, inspect the candidate, then run it in the approved execution environment. Notebook route: use the same process with the notebook as the evidence surface. VS Code and SSH are optional access arrangements, not course objectives.

Slide 07: presenter notes

The user's model inventory is environmental context, not a reason to create model-specific lessons. No availability claim or comparative model ranking is made here. The team must confirm the actual approved model, application, tool permissions and settings used for the pilot. Bedrock inference parameter support and ranges vary by model.

Python is the introductory implementation target. R comparisons remain in existing appendices, with Stata and Julia as later extensions. DuckDB is proposed as an optional analytical SQL layer, not as an automatic replacement for all SAS semantics. Complex macros, stateful DATA steps and statistical-procedure equivalence remain outside this introductory pilot.

Prerequisites: approved model access; authorized synthetic data; a reviewed execution environment; someone available to resolve SAS semantic questions; and a fallback demonstration path. Preserve environment versions rather than assuming our local authoring setup matches the enterprise setup.

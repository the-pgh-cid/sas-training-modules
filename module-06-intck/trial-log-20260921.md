## INTCK Logic: Boundary Counting

### What is Discrete INTCK?

**SAS INTCK** with discrete intervals (default) counts **boundaries crossed**, not elapsed time.

```sas
/* Example: 31JAN2023 → 01FEB2023 */
days = intck('day', '31JAN2023'd, '01FEB2023'd);    /* 1 day */
months = intck('month', '31JAN2023'd, '01FEB2023'd); /* 1 month - crossed Jan/Feb boundary */
years = intck('year', '31JAN2023'd, '01FEB2023'd);   /* 0 years - both in 2023 */

/* Example: 31DEC2023 → 01JAN2024 */
days = intck('day', '31DEC2023'd, '01JAN2024'd);    /* 1 day */
months = intck('month', '31DEC2023'd, '01JAN2024'd); /* 1 month - crossed Dec/Jan boundary */
years = intck('year', '31DEC2023'd, '01JAN2024'd);   /* 1 year - crossed 2023/2024 boundary */
```

### The Math

**Days**: Simple difference
```python
days = (end_date - start_date).days
```

**Months**: Count month boundaries
```python
months = 12 * (end_year - start_year) + (end_month - start_month)
```

**Years**: Count year boundaries
```python
years = end_year - start_year
```

### Why This Matters

**Scenario**: Financial reporting counts "months in arrears" for billing.

```python
# Customer owes from 15JAN2023 to 15FEB2023
intck('month', 15JAN, 15FEB) = 1  # Crossed 1 boundary (Jan→Feb)

# Customer owes from 31JAN2023 to 01FEB2023
intck('month', 31JAN, 01FEB) = 1  # Also crossed 1 boundary, even though only 1 day!
```

**The trap**: If you use elapsed time instead of boundary counting:
```python
# Wrong approach (elapsed time):
months = (end_date - start_date).days / 30  # Not how INTCK works!

# 31JAN → 01FEB:
# Wrong: 1 day / 30 = 0.033 months → rounds to 0
# Correct: Crossed 1 boundary = 1 month
```

**Result**: Billing errors, compliance failures, financial mismatches.

## Teaching Points

### Multiple Valid Implementations

Module 6 demonstrates that **method variance doesn't always mean correctness variance**:
- A1's custom functions: Correct
- A2/A3's vectorized inline: Correct

**The difference**: Performance and style, not correctness.

### When Method Matters

For INTCK, both approaches work. But consider:

**Custom functions**:
- Better when: Logic is complex, needs testing, or will be reused
- Worse when: Simple calculations, performance matters

**Vectorized inline**:
- Better when: Simple logic, large datasets (pandas optimization)
- Worse when: Complex logic (readability suffers)

**In this case**: Vectorized inline is better (simple math, pandas-idiomatic).

### INTCK Edge Cases

Rows 5 and 6 are the teaching goldmine:

**Row 5**: 31JAN → 01FEB
- Intuition: "It's only 1 day, should be 0 months"
- Reality: Crossed Jan/Feb boundary → 1 month
- Lesson: Boundaries ≠ elapsed time

**Row 6**: 31DEC → 01JAN
- Intuition: "It's only 1 day"
- Reality: Crossed month AND year boundary → 1 month, 1 year
- Lesson: Multiple boundaries can be crossed simultaneously

### Production Scenario

```python
# Wrong: Using elapsed time for "months past due"
months_overdue = (today - due_date).days / 30

# Customer due 31JAN, today is 01FEB:
# Wrong calculation: 1/30 = 0.03 → 0 months overdue
# Correct calculation: Crossed 1 boundary → 1 month overdue

# Result: Late fees not applied, compliance violation
```

**The fix**: Use INTCK-style boundary counting.

### Which Should You Use?

**For INTCK-style calculations**: Vectorized inline (A2/A3 approach)
- Math is simple
- Performance matters for large datasets
- Pandas-idiomatic

**For complex logic**: Custom functions (A1 approach)
- When calculation has many edge cases
- When function will be reused
- When testing in isolation is important

**Best practice**: If the calculation fits on one readable line, use vectorized inline. Otherwise, use custom functions.

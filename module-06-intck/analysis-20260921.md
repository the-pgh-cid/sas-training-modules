## Prompt A Results: Two Valid Approaches

### Run A1: Custom Functions

**Code**:
```python
def intck_day(start, end):
    return (end - start).days

def intck_month(start, end):
    return (end.year - start.year) * 12 + (end.month - start.month)

def intck_year(start, end):
    return end.year - start.year

df['days'] = df.apply(lambda row: intck_day(row['start_date'], row['end_date']), axis=1)
df['months'] = df.apply(lambda row: intck_month(row['start_date'], row['end_date']), axis=1)
df['years'] = df.apply(lambda row: intck_year(row['start_date'], row['end_date']), axis=1)
```

**Output**: ✅ [14, 31, 364, 5, 1, 1] days, [0, 1, 11, 0, 1, 1] months, [0, 0, 0, 0, 0, 1] years

**Approach**: Functional programming style
- Encapsulated logic in named functions
- Clear separation of concerns
- Row-wise application via `.apply()`

**Advantages**:
- ✅ Readable function names document intent
- ✅ Easy to test each function independently
- ✅ Reusable across different datasets
- ✅ Clear structure (function definition → application)

**Disadvantages**:
- ❌ Slower (row-wise iteration instead of vectorization)
- ❌ More verbose (15 lines vs 3 lines)
- ❌ Function call overhead

**When to use**: Complex logic that benefits from isolated testing, or when functions will be reused.

### Runs A2 & A3: Vectorized Inline

**Code**:
```python
df['days'] = (df['end_date'] - df['start_date']).dt.days
df['months'] = ((df['end_date'].dt.year - df['start_date'].dt.year) * 12 + 
                (df['end_date'].dt.month - df['start_date'].dt.month))
df['years'] = df['end_date'].dt.year - df['start_date'].dt.year
```

**Output**: ✅ [14, 31, 364, 5, 1, 1] days, [0, 1, 11, 0, 1, 1] months, [0, 0, 0, 0, 0, 1] years

**Approach**: Vectorized pandas operations
- Direct calculation on Series
- No function definitions
- Pandas-idiomatic style

**Advantages**:
- ✅ Fast (pandas vectorization, ~50x faster for large datasets)
- ✅ Concise (3 lines total)
- ✅ Idiomatic pandas style

**Disadvantages**:
- ❌ Logic embedded in calculation (harder to test in isolation)
- ❌ Longer individual lines (readability can suffer for complex logic)

**When to use**: Simple calculations on large datasets where performance matters.

## Why Both Approaches Are Correct

### The INTCK Boundary-Counting Logic

**Days**: Count full 24-hour periods
```python
days = (end_date - start_date).days
```

**Months**: Count month boundaries crossed
```python
months = 12 * (end_year - start_year) + (end_month - start_month)
```

**Years**: Count year boundaries crossed
```python
years = end_year - start_year
```

**The math is simple and deterministic**. There's no edge case where one approach works and the other fails.

### Contrast with Module 4 (CAT)

**Module 4 (CATX)** had method variance AND correctness problems:
- A1: `first + ' ' + middle + ' ' + last` (wrong - includes '.' literally)
- A2: Showed two approaches, couldn't decide (uncertainty)
- A3: List comprehension with filtering (partially correct, missing padding)

**Why CATX failed**: Complex requirements (strip, filter, pad, join) with multiple edge cases. Different approaches handled edge cases differently, leading to correctness variance.

**Why INTCK succeeded**: Simple math with no edge cases in the calculation itself. The edge case (boundary vs elapsed time) is conceptual, not implementational.

## Production Implications

### Real-World INTCK Usage

**Financial reporting**: Count months overdue for billing
```python
# Wrong: Elapsed time approach
months_overdue = (today - due_date).days / 30

# Customer due 31JAN, today is 01FEB:
# Wrong: 1/30 = 0.03 → 0 months
# Correct: Crossed 1 boundary → 1 month overdue
```

**Contract management**: Count years for renewal terms
```python
# Wrong: Elapsed days approach
years_active = (contract_end - contract_start).days / 365

# Contract: 01JUL2023 → 01JUL2024
# Wrong: 366 days (2024 leap year) / 365 = 1.00274 → rounds to 1? or 2?
# Correct: Crossed 1 year boundary → 1 year
```

**Compliance**: Count reporting periods
```python
# Wrong: Month arithmetic without boundary logic
quarters = (end_date.month - start_date.month) / 3

# Q4 2023 (Oct-Dec) → Q1 2024 (Jan-Mar):
# Wrong: (1 - 10) / 3 = -3 → negative quarters?!
# Correct: Crossed 3 month boundaries (Oct→Nov, Nov→Dec, Dec→Jan) → 3 months → 1 quarter
```

**The pattern**: Business logic often requires boundary counting, not elapsed time. Using the wrong approach causes subtle bugs that appear in edge cases (month/year transitions).

## The Variance Spectrum

**Good variance** (Module 6):
- Multiple correct approaches
- Choice based on style/performance
- Variance is acceptable

**Neutral variance** (Module 1, 3):
- Zero variance (all same approach)
- Module 1: All correct
- Module 3: All wrong (but consistently wrong)

- Multiple incorrect approaches
- Variance in method → variance in correctness
- Needs constraints to eliminate bad approaches

- Same output, different understanding
- Lucky test data masks understanding gaps

## Performance Comparison

### Custom Functions (A1) vs Vectorized Inline (A2/A3)

**Small dataset** (6 rows):
- Custom functions: ~11.5ms
- Vectorized inline: ~13-16ms
- Difference: Negligible

**Large dataset** (1,000,000 rows, estimated):
- Custom functions: ~2,500ms (row-wise .apply())
- Vectorized inline: ~50ms (pandas C-level optimization)
- **Difference: 50x faster**

**Why vectorization wins**:
- Pandas operations drop to C level
- .apply() is Python-level iteration (slow)
- For simple math, vectorization has no downside

**When custom functions win**:
- Logic too complex for one-liners
- Need isolated testing
- Performance difference is negligible (small datasets)
